# 多端协作分工方案

状态：待合并（PR #8 审查通过，合并后生效）

适用项目：AdBlock-Pro，以及后续由同一 GitHub 账号维护的其他项目

维护者：仓库所有者 / Ccmra404

## 1. 目标

让电脑、服务器和手机端插件可以并行工作，同时保证：

- GitHub `main` 是唯一事实来源；
- 一个任务只有一个主动写入者和一个工作分支；
- 电脑、服务器、手机端插件不会互相覆盖分支或重复实现；
- GitHub Actions、服务器测试和真实设备测试的结论彼此区分；
- 合并、发布和真机验收始终由维护者明确决定。

本方案是协作分工，不替代仓库中的 `AGENTS.md`、`CONTRIBUTING.md` 和 PR 模板；发生冲突时以仓库规则和维护者明确决定为准。

## 2. 角色分工

| 角色 | 主要职责 | 不负责的事项 |
| --- | --- | --- |
| GitHub 仓库 | 保存 `main`、主题分支、Issue、PR、Actions 结果和发布记录；Issue/PR 评论是持久交接记录 | 不把 CI 通过当作真机验收 |
| 维护者 / 用户 | 确认需求、决定任务归属、审查差异、合并 PR、发布版本、执行或确认真机验收 | 不要求其他端代替最终授权 |
| 电脑端 | 交互式调试、复现问题、编写代码、人工审查和设备联调 | 不与服务器同时写入同一主题分支 |
| 服务器端 | 独立工作副本、长时间构建、集成测试、日志/环境诊断，以及被明确分配的代码任务 | 不直接修改 `main`，不自行合并或发布 |
| 手机端插件会话 | 快速分析、局部优化、代码审查、PR/Issue 操作和小范围验证 | 默认只读独立审查，不自动取得他端主题分支的写权限；不接管服务器分支，不在同一任务上与电脑端重复提交 |
| GitHub Actions | 对 PR 的目标提交执行自动化检查、ARM64 测试包和构建验证 | 不替代真实 Android 设备测试 |

“服务器端”是工作端，不是新的主仓库；“手机端插件”是协作会话，不是一个需要长期占用同一分支的开发者身份。

## 3. 分支与任务归属

### 3.1 一个任务一个分支一个主动写入者

分支按照任务命名，不按照设备命名：

```text
feat/<scope>-<topic>
fix/<scope>-<topic>
perf/<scope>-<topic>
docs/<topic>
chore/<topic>
```

电脑、服务器或手机端插件一旦成为某个任务的主动写入者，该端就是该分支的唯一写入者。其他端只能读取、测试、评论或提出补丁建议。

禁止以下行为：

- 多个端同时 push 同一个主题分支；
- 直接在 `main` 上开发或推送；
- force-push、重置或改写其他端未完成的分支；
- 将两个独立任务堆在同一个分支或提交中；
- 把旧 PR 的绿色 CI 当作新提交的验证证据。

### 3.2 当前基线与过渡状态

电脑端和手机端现有优化的合并过渡已经完成，PR #7 已合并。服务器不再处于合并等待冻结阶段；从现在起按任务归属获得写入权后即可开展独立工作：

1. 开始任何任务前，服务器执行 `git fetch origin --prune`，核对 `git rev-parse origin/main` 的完整 SHA；`b93baa04cb132b26858015361ff12246b8ded20d` 仅是 PR #7 合并完成时的历史基线，不是永久固定的最新版；
2. 维护者明确分配任务后，主动写入者从该最新 `origin/main` 创建任务分支，并在交接记录中写明基线 SHA；
3. 在获得具体任务归属前，服务器只读、验证和评论，不自行占用他端主题分支；
4. 如需临时验证旧 PR，使用 detached worktree，验证结束后删除临时工作区，不 push；
5. 服务器不会把 `main` “搬到自己这里”。服务器本地 `main` 只是 GitHub `origin/main` 的工作副本，GitHub 仍然是主源。

PR #8 创建时早于 PR #7，更新本 PR 时采用正常的 `merge`/分支更新方式同步新基线，不 force-push、不重写已有提交；PR #8 的变更范围仍只限本协作文档。

### 3.3 依赖未合并 PR 的任务

默认从最新 `origin/main` 开始。如果任务确实依赖未合并 PR，必须在 PR 描述中写明：

- 依赖的 PR 编号和 head SHA；
- 为什么不能从 `main` 独立实现；
- 依赖 PR 合并后需要如何同步和重新测试。

不能把一个整合 PR 和它已经选择性包含的组件 PR 无判断地全部合并，避免重复提交和冲突。

## 4. 标准工作流

### 协调中心与主动读取

[多端协作中心](https://github.com/Ccmra404/multi-terminal-collaboration-hub) 是三端共享的任务目录和协调入口，不是自动代理已经上线的声明，也不是可以直接执行命令的队列。每个实际任务仍必须建立独立 Issue、指定一个唯一 owner、创建一个主题分支和对应 PR；`main` 是代码事实来源，任务 Issue 和 PR 评论是进度、测试和交接的持久事实来源。

电脑端、服务器端或手机端收到“检查最新进度”“继续我的任务”等指令时，必须主动读取：

1. Issue #9 协调中心；
2. 对应的任务 Issue 和 PR 审查/评论；
3. 最新 `origin/main` 完整 SHA；
4. 与当前提交 SHA 对应的 GitHub Actions/CI 结果。

不能把三个独立聊天会话当作实时同步渠道，也不能把上次聊天中的文字当作最新状态。没有直接读取 GitHub 能力的端，才请维护者代为补充信息。

### 开始任务

主动写入者开始前报告：

```text
项目/任务 Issue：
工作端/唯一写入者：
当前状态：待办 / 执行中 / 待审核 / 被阻塞 / 已完成
origin/main 基线完整 SHA：
分支/PR、最新 HEAD SHA：
本次成果：
测试证据（环境、结果、对应 SHA）：
未覆盖/失败测试：
风险与恢复方式：
下一个工作端：
是否需要维护者审批：否 / 是（具体事项）
```

服务器端的标准步骤：

```bash
git fetch origin --prune
git switch main
git pull --ff-only
git switch -c <type>/<scope>-<topic>
```

### 开发与交接

每次交接必须在任务 Issue 或 PR 评论中使用上面的固定格式，至少说明：

```text
项目/任务 Issue：
工作端/唯一写入者：
当前状态：
origin/main 基线完整 SHA：
分支/PR、最新 HEAD SHA：
本次成果与已修改文件：
测试环境、结果及对应 SHA：
未覆盖/失败测试与真机范围：
风险与恢复方式：
下一个工作端：
是否需要维护者审批：
```

日常进度直接写入任务 Issue 或 PR；只有授权、故障阻塞或阶段验收需要维护者决策。维护者在任一端提出查询时，由该端自行读取 GitHub 并概述，不要求维护者在三端之间手工转发。

其他端发现问题时，优先在 PR 中评论或新建独立修复分支，不直接改写当前任务分支。任何评论只代表提案、审查或交接，不代表已执行：不得仅凭 Issue/PR 评论自动合并、发布、改 tag、覆盖 Release、重启设备或执行危险防火墙/Root 操作；这些动作仍须维护者明确批准。

### 合并与发布

- Draft PR 由主动写入者维护，目标通常为 `main`；
- GitHub Actions 必须对应当前 PR 的最新 head SHA；
- 维护者决定是否合并；
- 合并后维护者决定是否执行真实设备测试；
- Release、tag、正式 ZIP 和版本号变更必须得到维护者明确授权；
- 未经授权，服务器和手机端插件都不得自行合并或发布。

服务器端持续监听 GitHub、驱动代理或自动同步任务属于后续独立任务，不纳入本 PR。若要实现，先另建 Issue，评估 GitHub 原生通知、Actions、Webhook 或轮询方案，并单独审查凭据最小权限、部署、可观测性、幂等、防循环和失败重试；在完成前不得把概念方案描述为已部署。

## 5. 测试职责

| 测试类型 | 首要执行端 | 结论含义 |
| --- | --- | --- |
| Shell/Node/Go 单元与语法检查 | 服务器或 GitHub Actions | 代码/模拟环境检查通过 |
| ARM64 测试 ZIP、结构和凭据排除 | GitHub Actions，服务器可复核 | 当前提交的构建检查通过 |
| 长时间任务、日志、环境诊断 | 服务器 | 服务器环境下的集成证据 |
| 交互式调试和问题复现 | 电脑 | 便于定位和修复 |
| KernelSU/Magisk/APatch、安装升级、重启、网络 | 真实 Android 设备 | 真机证据，不能由 CI 或服务器替代 |

报告测试时必须写明实际工作端、具体 commit SHA 和测试类型，不能只写“测试通过”。代码改动与核验结论也必须标注实际产生它们的电脑、服务器或手机端插件会话。

## 6. 多项目管理

服务器为每个仓库使用独立目录：

```text
/root/projects/<repository-name>
```

每个仓库分别维护自己的 remote、分支和 PR。不同项目之间不共享工作目录、不复用未完成分支、不混用版本号或测试结论。

服务器的 GitHub SSH 身份只应覆盖实际授权的仓库，遵循最小权限原则；它可以访问多个已授权仓库，但每个仓库仍然遵守“一个任务一个分支一个主动写入者”。

GitHub 私有仓库也不得在 Issue、PR 或交接中粘贴 `admin.auth`、设备识别符、个人 DNS 抓包原始数据、含凭据日志或其他未脱敏敏感信息，只记录去标识、无凭据的摘要。

## 7. 本方案的当前执行结论

- Issue #9 是三端共享的协调目录；每个实际任务必须落到独立 Issue、唯一 owner、主题分支和 PR，日常交接写入 Issue/PR 评论；
- 各端开始或继续任务前主动读取协调中心、任务 Issue、PR 审查、最新 `origin/main` SHA 和对应 SHA 的 CI，不把独立聊天会话当作实时同步；
- 电脑端/手机端 PR 的合并过渡已经完成；PR #7 合并时的 `b93baa04cb132b26858015361ff12246b8ded20d` 仅作历史锚点，当前基线必须在每项任务开始时重新读取 `origin/main`；
- 服务器在获得具体任务归属后，先 fetch/prune 并核对最新 `origin/main` 完整 SHA，再创建自己的任务分支；
- 服务器负责可重复构建、集成测试和被分配的代码任务；
- 电脑负责交互式调试和人工联调；
- 手机端插件默认负责只读独立审查、快速分析和独立小任务，不自动获得他端分支写权限；
- 同一任务的代码提交与测试结论必须写明实际工作端和提交 SHA；
- Issue/PR 评论是提案、审查或交接，不是自动执行命令；合并、发布、改 tag、覆盖 Release、重启设备和危险网络/Root 操作仍须维护者明确批准；
- 服务器持续监听或驱动远端代理属于后续独立任务，必须另建 Issue 评估和部署；
- 维护者负责最终合并、真机验收和发布。
